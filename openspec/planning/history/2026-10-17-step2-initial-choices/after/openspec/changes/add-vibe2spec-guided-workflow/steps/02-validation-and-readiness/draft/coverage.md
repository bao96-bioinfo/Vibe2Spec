# Step 2 coverage proposal

## Status and authority

This is an unapproved planning draft for Step 2. It proposes how to divide validation responsibilities and how to design the eventual checks. It authorizes no implementation, test execution, fixture modification, filesystem access, dependency installation, or change to an accepted step. The user has accepted Step 1 and approved the ten policies in [the response evidence](../decisions/policy-responses-v1.md). The selected paired unit is now the record-envelope checker. References below to the selected function's pending specification concern its detailed interface, fixtures, expected findings, and limits. Exact validation details still require specification and approval.

The accepted sources are `docs/record-format.md`, `tests/fixtures/records/base.json`, `tests/fixtures/records/cases.json`, and the Step 1 revision 4 fixture contract. The Step 2 roadmap and `openspec/planning/vibe2spec-step-02-interview.md` identify the work still requiring specification. Accepted record fields, state meanings, fixture contents, and existing expected finding categories remain unchanged.

This proposal defines coverage categories. It is not a complete execution specification. Exact public interfaces, diagnostic messages, report fields, evaluation order within each assessment, concrete additional fixture values, test counts, commands, runtime, locations, and resource bounds still need explicit approval. The eventual specification must resolve each item before code preparation.

## Assessment boundaries

A mechanical check evaluates a rule that has a specified deterministic interpretation, such as whether a referenced file has the approved digest. A semantic review evaluates meaning and supporting evidence, such as whether a method description leaves an argument unspecified. A later workflow operation performs or verifies lifecycle transitions, executes comparisons, or obtains host evidence. These responsibilities overlap without being interchangeable.

| Responsibility | Proposed Step 2 coverage | Remaining responsibility |
| --- | --- | --- |
| Record structure | Load the selected records and check declared versions, field inventories, types, conditional fields, ordering, and identities. | A valid shape does not establish that the described behavior is complete or scientifically appropriate. |
| Content identity | Check accessible approved paths, retained bytes, reference kinds, project identity, digest and byte-size claims, snapshots, and cycles. | The caller and reviewer establish that reading each workspace or external location is authorized. A path appearing in a record supplies no such approval. |
| Implementation readiness | Check the complete current-step package, linked units, decision coverage, applicable approvals, explicit pairing choice, current dependencies, and exact passing specification-review evidence. | The separate reviewer assesses method completeness, genuine approval provenance, and actual context independence. |
| Prepared-work evidence | Check the structure and identity of a supplied prepared-work snapshot and its pre-execution review. The interview must decide whether Step 2 exposes a separate execution-readiness assessment or only these reusable structural checks. | Step 5 specifies actual worker handoff, inspection of code and effective settings, and execution protocol. A helper never executes a command read from a record. |
| Comparison evidence | Check record structure, references, rule declarations, check identities, and associations between saved runs and results. | Step 6 supplies approved comparison algorithms and independent implementation evidence. Step 2 does not infer a numerical formula from prose or recalculate scientific results. |
| Completion and reopening | Check record shapes and exact references, and prevent missing or stale dependency evidence from establishing current readiness. | Step 7 owns transition automation, completion, renewed acceptance, reopening scope, suspension, and resume selection. Step 2 neither marks steps finished nor edits project state. |

The report must separate structural validity, unresolved required information, readiness, and an assessment that could not be completed. Their exact representation remains a decision. In particular, a valid pending project state is not an error, and it grants no permission to perform the activity for which approval or review is pending. An inaccessible required file or exhausted resource bound cannot produce a passing assessment.

## Existing fixture interpretation

The accepted fixture container is a virtual workspace. Its JSON artifacts have the exact serialization specified in the Step 1 fixture contract, and its text artifacts have their stated UTF-8 bytes. Each case starts independently from the untouched base graph. Changes follow their listed order. The case's `reference_policy` determines whether dependent references are rebuilt or preserved. Step 2 must specify a test adapter for this representation before implementing one. The adapter must never run stored commands or apply mutations to accepted fixture files or actual project records.

The `assessment` field limits what an existing case asserts. Its `expected_codes` are retained as the accepted finding categories for that assessment. A helper's new report cannot silently replace those expectations with a broader set of unrelated findings. Conversely, a case with an empty expected-code array does not establish that every possible gate passes.

For historical state cases, the usable evidence is the selected state record's references and their transitive targets. Later events elsewhere in the reusable container cannot satisfy an earlier gate. Selecting the entry record, traversing references, and reporting unassessed obligations must be specified independently from choosing a latest live project revision.

No narrowed check may be described as the full original assessment.

## Common rule coverage

The following rules come from the accepted format. The proposed tests must cover their valid and invalid forms without adding undocumented workflow fields or changing the format. The additional parsing and filesystem policies identified in the last column remain interview decisions where the accepted format does not fully determine implementation behavior.

| Rule area | Required coverage | Specification decisions and residual limits |
| --- | --- | --- |
| Raw JSON and decoding | Require a record object with all envelope fields; detect malformed JSON and unsupported numeric representations before information is lost. Preserve information needed to recognize repeated keys, original field order, and numbers that ordinary parsing would round. | Fix UTF-8 decoding, byte-order-mark treatment, repeated-key diagnostics, lexical number handling, nesting limits, and error locations. Do not implement a parser policy from a conventional default. |
| Envelope | Check exact version, enumerated kind, identifier grammar and maximum length, positive safe revision, project identity, context, lifecycle, Actor fields, and non-null content object. Check listed field order and closed inventories. | Specify dispatch and findings when version or kind is unsupported; an unsupported format must not be guessed. |
| Shared objects | Cover every declared field, type, allowed enumeration, collection condition, and field order in Response, Requirement, Check, Output, Finding, CheckResult, EffectiveSetting, Command, Edit, ResourceUse, and each Rule variant. | General JSON values and decision literal objects are data. They do not inherit a closed workflow field inventory or become executable expressions. |
| Null and collections | Distinguish unresolved declared draft content from permitted literal or field-specific null values. Preserve specified empty arrays and maps. Reject unknown fields in drafts as well as frozen records. | Specify how unresolved locations are reported. No global rule may turn every null into an error or every empty collection into missing information. |
| Numeric support | Enforce field-specific integer bounds and positive or nonnegative restrictions. Reject unsupported numeric representations without silent rounding. Preserve exact supported values and the approved interpretation of strings representing larger integers. | Determine token-level handling, report representation, and boundary cases. Numerical tolerance strings still require semantic review of their interpretation. |
| Identity and revision | Detect duplicate `(id, revision)` pairs in one project graph, changes of kind or project for one identity, and incompatible references to the same preserved revision. | Revision-history checks require a specified retained-history input. A selected historical graph cannot prove which revisions exist elsewhere or whether every past version was preserved. |
| Context separation | Keep `authoring`, `example`, and `project` meanings distinct; validate the explicit fictional and template actor conventions where applicable. | Example and authoring records cannot pass a real project gate. Tests may assess their fictional internal relationships without changing their context. |
| Approval coverage | Resolve approval snapshot and target paths, verify exact target bytes, recognize the selected approval purpose, and check coverage of all required step, unit, decision, normative document, fixture, and check-definition artifacts. | Genuine response provenance and whether prose is an explicit applicable approval require separate review. A nonempty response string supplies structure alone. |
| Review evidence | Require exact frozen scope, matching author and reviewer, appropriate phase, passing outcome with no unresolved findings, complete declared author coverage where derivable, and distinct context identities. | Non-record authorship and actual context separation require handoff evidence. Missing provenance remains unresolved. |
| Assessment ordering | Assess parseability and envelope before field and reference checks, then applicable context, approval, completeness, review, comparison, and lifecycle obligations. Stop following broken references and retain independent findings. | Fix deterministic diagnostic order, duplicate suppression, prerequisite failures, and incomplete-assessment reporting. Semantic obligations cannot silently be marked passed by a mechanical stage. |

## Implementation and prepared-work readiness coverage

Implementation readiness must examine the entire selected current step and all applicable linked units. A complete unit cannot compensate for an unresolved step contract. A preserved draft is still unresolved. A frozen recommendation without exact approval remains unapproved. A passing reviewer record with the wrong scope, phase, or context cannot fill the missing gate.

The proposed check inventory includes complete required field coverage, required decision closure including derived inputs, applicable approval targets, exact normative artifacts and fixtures, explicit resource decisions, all output Rule declarations, per-step pairing choice, and passing separate specification review. Dependency readiness requires exact accepted revisions and must remain unavailable when necessary dependency evidence is missing, stale, or suspended. Complete lifecycle analysis remains assigned to Step 7; the Step 2 interface must expose any dependency obligation it cannot establish instead of treating it as satisfied.

Prepared-work checking adds identity checks for the preserved implementation, commands, configuration, effective settings, and exact passing pre-execution review. These are checks on supplied evidence. Whether actual code uses an extra parameter or an inherited default generally requires the separate reviewer's analysis. No Step 2 helper may claim that record coverage alone proves absence of unapproved implementation choices.

If a supplied review includes earlier reviewers' records, its independence assessment includes their contexts as assessed authors. Reusing a specification reviewer to review a later scope containing that review cannot satisfy the accepted independence rule. Missing non-record author provenance must remain visible rather than being omitted from the assessed scope.

The approved Step 2 pairing policy applies to one small function. The selected unit still needs its own complete interface, fixtures, expected findings, and direct comparison rule. These checks supplement the whole helper's specified tests. They do not require duplicating the entire validator. The two implementations must be checked individually against expected results as well as directly against one another; two matching errors cannot pass correctness.

## Remaining specification decisions

The complete Step 2 contract must carry forward the approved built-in-module policy, both report modes, and pairing of one small function. It must fix callable and command-line interfaces, entry-record and scope selection, runtime and module format, exact access authority, report and exit behavior, raw parsing rules, reference traversal, deterministic diagnostic ordering, retained-history inputs, resource bounds, test-adapter behavior, and the treatment of incomplete assessments. The user must decide whether a separate execution-readiness operation belongs in this step or whether Step 2 provides structural prepared-work checks for the later worker protocol.

Some accepted rules require information that JSON alone does not provide, including genuine user approval, actual reviewer independence, authorship of non-record artifacts, and semantic agreement between prose and settings. The specification must identify the evidence expected for each such obligation and how the helper reports the limits of its assessment. It must not create new version 1 workflow fields to hide that gap.

The proposed coverage leaves accepted Step 1 artifacts intact. If completing the specification reveals an unavoidable change to the accepted format, the coordinator must explain the necessity, enumerate every affected file and planned modification, and obtain exact-scope reopening approval before changing that step. No such amendment is established by this planning draft.
